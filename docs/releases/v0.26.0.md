0.26.0 adds OpenRouter as a second source of models: a task can run on an OpenRouter model, switch between Claude and
OpenRouter mid-conversation, and start children on the other source. It is a first landing, usable but unfinished;
what isn't done is listed below.

- **Connect OpenRouter in Settings.** Settings › Models connects an API key while your Claude account stays active.
  The key is encrypted (Electron `safeStorage`, backed by the system keychain) before it's saved, and a snapshot
  never contains it; there's no way to view it again, only **Replace key** or **Remove**. Connecting discovers its
  tool-capable text models and hosting providers; search or filter the catalog, choose a provider for each model you
  want, then enable its checkbox to offer it.
- **Run a task on an OpenRouter model** from the task picker, alongside Claude models. Most things work as on
  Claude, but an OpenRouter task uses separate Claude Code user configuration: your user instructions, skills,
  agents, commands, hooks, plugins, user MCP servers and existing auto-memory don't carry over (project
  configuration and Glade's own tools still load). They come back when you switch to Claude.
- **Switch a task between sources mid-conversation**, keeping its history. Allowed while idle, stopped on an error,
  or paused on a Claude usage limit, where switching to OpenRouter resumes the held turn at once. Refused during a
  running turn, with an open question/permission card, or on an idle task with live background work still going.
  Switching off a limit pause stops that task's watchers and children with a recorded reason, and tells the new
  session which ones stopped so it can restart what it needs.
- **Children on the other source.** The main agent still starts same-source subagents with the built-in `Agent`
  tool, keeping its agent types, worktree isolation and `SendMessage`. With an OpenRouter key connected, it also
  gets a `dispatch` tool (with `list_models` to see what's available) to start a child on the *other* source only.
  A dispatched child starts at Low effort, inherits the main prompt and tools with metadata/control calls refused,
  and has no agent-type selection or native worktree isolation yet.
- **The usage meter shows both.** Claude's plan usage reads as before, plus a separate OpenRouter row in USD
  (remaining key allowance, or spend when uncapped). The two are never summed.
- **Nothing changes for a task that never touches OpenRouter**, and with no key connected, sessions start exactly
  as they did in 0.25.

## Not done yet (follow-ups)

- A test asserting the note a limit-switch gives the new session.
- Dispatched children start at Low effort; inheriting the parent's effort or a per-dispatch choice is a follow-up.
- Dispatched children inherit the main prompt and tools; a child-specific prompt/tools, agent types and native
  worktree isolation aren't built.
- A limit-switch stops all children, even ones on the source the limit didn't affect; keeping those alive is
  deferred.
- A busy switch (running turn, open card, or idle background work) is refused outright; saving it for the next
  safe moment isn't built.
- Changing Claude models from the picker doesn't clear a Claude usage-limit pause.
- Neither source reports a per-task or per-child billed cost.
- Choosing another provider disables the old pair for existing tasks and resets affected defaults to Claude,
  rather than migrating them.
- Usage accounting has timing gaps (a turn's first request, a child's final read, blocked-key detection, a negative
  remaining allowance, a malformed cached row) that need more coverage.
- Earlier preview databases may still carry unused `tasks.subagent_model`/`openrouter_generations` tables; removing
  them is deferred.
- Production-prompt dispatch in both directions, upgraded SDK todos across a switch, several relaunch/resume
  scenarios and full SDK runtime/UI integration still need validating.
- Native children only run on the parent's route; cross-route dispatch, an OpenRouter → OpenRouter run on a
  different route, and a thinking block carried back to Claude are unverified.

## Under the hood

- Migrations added since v0.25.0:
  - **0065**, for OpenRouter itself: the encrypted key and cached catalog, curated model/provider choices, usage
    readings, model-switch history, and the SDK transcript tables that preserve chat/tool history across a source
    switch.
  - **0066**, for independently routed children: the `managed_agents` table that tracks a dispatched child's model,
    session and state, plus repairs for preview databases made by earlier revisions of the unmerged branch.
- **Back up your data folder before first launch: these migrations are forward-only, and 0.25 can't safely open the
  database afterwards.**
- The sandbox switch still defaults to off (`sandboxEnabled: false` in `src/shared/settings.ts`).

## Running it

- **Back up your data folder before first launch: this release's migrations are forward-only, and 0.25 can't
  safely open the database afterwards.**
- **Requirements:** a Mac with Apple silicon, logged in to [Claude Code](https://docs.claude.com/en/docs/claude-code).
- **Auth:** Glade runs on your own Claude Code login (or `ANTHROPIC_API_KEY`, if you have one set). It never asks for or
  stores your credentials.
- **Install:** download `Glade-0.26.0-arm64.dmg` below, open it and drag Glade to Applications. Your workspaces and
  tasks from 0.25.0 carry over.
- **First launch:** Glade isn't notarised by Apple yet, so the first time, right-click Glade in Applications and choose
  Open (on newer macOS, if there's no Open button, click Open Anyway in System Settings → Privacy & Security). If macOS
  still won't open it, run `xattr -dr com.apple.quarantine /Applications/Glade.app` and try again.
- **Logs:** `~/Library/Logs/glade/main.log`, one JSON line per event, rotated at 5 MB. They stay on your Mac;
  attach them to a bug report if you like (`docs/logs.md` says what's in them).
